## 1. 목표 + 3기둥

**목표:** 라이트 유저가 **자기 컴 사양에 맞게** 에이전트 부대를 굴리고, **위험한 몇 개만 빼고** 자율로 돌리며, 에이전트들이 **A2A로 협업**해 큰 걸 만들되 — **다 기록되고 언제든 되돌릴 수 있어** 안 무섭다.

- **기둥 1 · 조절 가능한 안전장치** — 위험 액션을 설정에 카탈로그화, per-action 토글 + 오토모드 프리셋. 단 "절대 못 끄는 하드락" 소수는 남긴다.
- **기둥 2 · 스펙 인식 동시성** — 하드코딩 4 → 컴 사양 읽어 **추천값 + 슬라이더**(게임 그래픽 세팅처럼).
- **기둥 3 · A2A 스웜** — 플랜(DAG) → 병렬 실행 → 런타임 동적 핸드오프 → 통합.

## 2. 기둥 1 — 안전장치를 "설정 가능한 정책"으로

**원칙:** 브레이크를 *없애는* 게 아니라 **유저가 강도를 고르게.** 그리고 "다 auto"여도 **최소 하드락**은 남겨 신뢰 마지노선 유지.

### 2.1 액션 카탈로그 (한 곳에 정의)
지금 `surface-approval.ts`에 흩어진 걸 **단일 카탈로그**로. 각 액션 = `{ id, 라벨, 위험도 tier, 기본정책 }`:

| tier | 예시 액션 | 기본 |
|---|---|---|
| 🟢 낮음 | 파일 읽기·생성, 코드 작성, 스캐폴드, 도구 스모크 | auto |
| 🟡 중간 | 패키지 install, 외부 서비스 connect, 브라우저 위임, 자료 발행 | 오토모드에 따라 |
| 🔴 높음(하드락 후보) | **실제 결제/돈 지출**, **계정 비번·시크릿 노출**, **데이터 영구 삭제**, **프로덕션 배포** | 항상 최소 1회 확인 |

(현재 이미 `request-payment-approval`은 항상 체크포인트 — 이걸 하드락의 시작점으로.)

### 2.2 per-action 정책 + 오토모드
- 액션별 정책: **`ask`(물어봄) / `auto`(알아서) / `block`(금지)** — 설정 페이지에서 토글.
- **오토모드 프리셋(슬라이더 1개로 일괄)**: `안심`(거의 다 ask) → `균형`(🔴만 ask) → `풀오토`(**진짜 전부 auto — 하드락 없음**).
- 기존 `autonomy.mode`(agent-operated/supervised)를 이 정책 스토어로 승격·확장.

### 2.3 풀오토 = 진짜 전부 해제 (하드락 없음) — 안전은 "차단"이 아니라 "동의 + 기록"으로
**유저 결정:** 풀오토는 결제·삭제·배포·시크릿까지 **전부 auto.** 강제로 못 끄는 게이트는 두지 않는다. 대신 안전 모델을 *사전 차단*에서 *사후*로 옮긴다:
- **일회성 정보 동의(informed opt-in):** 풀오토를 켤 때 **딱 한 번** — "모든 브레이크를 풉니다. 에이전트가 결제·삭제·배포까지 알아서 합니다." 확인 → 이후엔 안 물어봄.
- **전부 기록 + 되돌리기(변경 영수증):** 사전 차단 대신 사후 취소. → [plan-change-receipts.md](./plan-change-receipts.md) 필수 선행.
- **⚠️ 정직한 한계(되돌릴 수 없는 것):** 실제 돈 지출 · 외부 발송(메일/메시지) · 3rd party 영구 삭제는 **물리적으로 undo 불가.** 풀오토를 켠다 = 이건 **못 되돌린다는 걸 받아들인다**는 뜻. 그래서 이 부류만 영수증에 **"취소 불가"** 라벨로 사후에라도 또렷이 보이게(막지는 않음, 표시만).
- **커스텀 유지:** 풀오토여도 개별 토글로 "결제만은 물어봐"처럼 특정 액션만 다시 ask로 뺄 수 있음.

### 2.4 되돌리기와 결합 (핵심)
**브레이크를 풀 수 있는 이유 = 변경 영수증(짝꿍 기획).** auto로 뭘 했든 **전부 기록 + 되돌리기 가능**하면, 사후에 취소할 수 있으니 사전 게이트를 줄여도 안심. → 두 기획은 **한 세트.**

**건드릴 곳:** `renderer/lib/surface-approval.ts`(정책을 설정에서 읽게), 신규 `policy` 설정 스토어 + IPC, 설정 페이지 UI(액션 목록+토글+프리셋), `autonomy.mode` 확장.

**자평(스크린샷 테스트):** ✅ 게임 세팅처럼 "이 에이전트에게 어디까지 맡길지" 한 화면에서 고르는 건 비개발자도 직관적. "풀오토 + 되돌리기 있음"이 안심 카피.

## 3. 기둥 2 — 스펙 인식 동시성 슬라이더 (게임 그래픽 세팅처럼)

### 3.1 스펙 읽기 → 추천값
- 메인 프로세스: `os.cpus().length`, `os.totalmem()` (필요 시 GPU/플랫폼). 렌더러 폴백: `navigator.hardwareConcurrency`, `navigator.deviceMemory`.
- **추천식(초안):** `recommended = clamp( min( cores - 2, floor(freeRAM_GB / 에이전트당_예상RAM) ), 1, 상한 )`. 에이전트 1개 ≈ 무거운 CLI/모델 프로세스라는 현실(← 방금 한 perf 감사) 반영.
- 미지수 U-A: 에이전트당 실제 메모리 프로파일(추천식 계수 튜닝) → 실측 필요.

### 3.2 UI (대시보드/설정)
- **슬라이더** + "**추천: 6**" 배지 + 프리셋(`저사양`/`균형`/`고사양`/`커스텀`).
- 게임처럼 **정직한 경고**: 추천 초과 시 "이 값이면 앱이 느려질 수 있어요"(제 perf 감사가 근거). 
- 값은 firm/borrowed/stormbreaker 세 경로에 **동일 적용**.

### 3.3 주입
- `MAX_*_PARALLEL` 하드코딩 제거 → 설정값 주입: `parallelCap(items, settings.concurrency, …)`.
- stormbreaker: `run_stormbreaker_decision(max_workers=설정값)`, `execution_fabric` `max_parallel`도 설정 반영.

**건드릴 곳:** 신규 `system-specs` IPC(os 읽기) + 추천 계산, 동시성 설정 스토어, `firm-orchestrator.ts`/`borrowed-task-force.ts` 상수→주입, `stormbreaker_runner.py` max_workers 전달, 대시보드/설정 UI.

**자평:** ✅ 님이 콕 집은 그림 그대로. "내 컴에 맞게 추천 + 내가 다이얼로 조절"은 즉시 이해됨. **P0 1순위**(가장 쉽고 체감 큼).

## 4. 기둥 3 — A2A 스웜 오케스트레이션 (플랜부터)

### 4.1 지금 vs 목표
- 지금: **위계 중앙집중** + **정적 DAG**(stormbreaker execution_fabric는 사전에 packet/의존성 확정). 런타임 중 에이전트가 새 일을 만들거나 피어에게 자유롭게 넘기는 **emergent 핸드오프가 없음.**
- 목표: **플랜 → 병렬 실행 → 런타임 동적 핸드오프 → 통합**의 스웜.

### 4.2 4단계 설계
1. **플랜(먼저):** 계획 에이전트가 목표를 **태스크 그래프(DAG)**로 분해(노드=작업, 엣지=의존). → `execution_fabric.py`(이미 packet/depends_on/parallel_groups 생성) **재활용·확장.**
2. **병렬 실행:** 준비된(의존성 충족) 노드를 **동시성 슬라이더값**만큼 워커가 동시 실행. → `stormbreaker_runner.py`(ThreadPool) 재활용.
3. **A2A 동적 핸드오프(신규 핵심):** 워커가 실행 중 "이건 X 전문가가", "새 서브태스크 필요" → **그래프에 노드/의존성을 런타임에 추가**하거나 피어에게 위임. 결과 교환은 **공유 블랙보드**(공유 메모리/작업물 폴더)로. ← 지금 없는 유일한 진짜 신규.
4. **수렴/통합:** 종합 에이전트가 산출물 통합 + 완료/막힘까지 루프(오토모드 정책 하). 루프 바운드(3/2)를 **오토모드에서 설정 가능하게** 완화.

### 4.3 재활용 vs 신규
- **재활용:** execution_fabric(DAG) · stormbreaker_runner(병렬) · firm 위임(자율 선택) · a2a.py(외부 에이전트 발견).
- **신규:** ⓐ 런타임 그래프 동적 확장 ⓑ 공유 블랙보드 스토어 ⓒ 피어 핸드오프 프로토콜 ⓓ 오토모드에서 루프 바운드 완화.

**건드릴 곳:** `execution_fabric.py`(동적 노드), `stormbreaker_runner.py`(런타임 그래프 재평가), 신규 블랙보드 스토어, 오케스트레이터(플랜→실행→수렴 루프), `loop-engineering.ts`(바운드를 설정 연동).

## 5. 로드맵 (P0 → P3)

| 단계 | 내용 | 왜 이 순서 |
|---|---|---|

## 6. 리스크 · 미지수

- **R-1 (풀오토는 진짜 사고 가능 — 하드락 없음, 유저 결정):** 강제 게이트가 없으므로 안전은 전적으로 **① 켤 때 정보 동의 ② 변경 영수증(되돌리기)**에 의존. 되돌릴 수 없는 액션(실지출·외부발송·영구삭제)은 undo 불가 → 영수증에 "취소 불가" 강조. **∴ 변경 영수증 기획이 풀오토의 필수 선행조건.**
- **R-2 (단일 머신 한계):** 93 병렬은 한 대에선 물리적으로 못 버팀(방금 perf 감사가 증명). 슬라이더가 **정직하게 경고**하고, 진짜 대규모는 분산/클라우드(별도, hep-storm `--executor-command`가 씨앗).
- **R-3 (스웜 조율 품질):** "93 표현 가능" ≠ "일관된 OS 산출". 플랜/블랙보드/수렴 설계가 성패. 데모의 매끈함은 큐레이션 큼.
- **R-4 (오토모드 오남용):** 유저가 뭔지 모르고 풀오토 → 사고. 프리셋 기본은 `균형`, 풀오토는 명시적 경고 + 되돌리기 강조.
- **U-A:** 에이전트당 실제 RAM/CPU 프로파일(추천식 계수) → 실측 필요.
- **U-B:** `execution_fabric` 동적 노드 추가 난이도(현재 정적 가정 깊이) → `stormbreaker_runner` 재평가 루프 확인 필요.
- **U-C:** 블랙보드(공유 작업물) 충돌 — 두 에이전트가 같은 파일 → 변경영수증의 충돌 감지와 연결.

## 7. 안전 철학 (한 줄)
**풀오토는 브레이크를 진짜로 다 풀 수 있다(유저 선택).** 안심의 근거를 "차단"이 아니라 **"켤 때 한 번의 정보 동의 + 뭘 하든 다 기록·되돌리기"**로 옮긴다. 단 실지출·외부발송·영구삭제는 되돌릴 수 없으니 **그것만은 영수증에 또렷이**(막지 않고 표시). — Antigravity 데모(무개입·**무기록**)와 갈리는 지점은 "게이트 유무"가 아니라 **"모든 걸 기록하고 되돌릴 수 있게 해서, 풀어도 안심"**이라는 점.
